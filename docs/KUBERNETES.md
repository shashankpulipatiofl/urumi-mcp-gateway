# Kubernetes: what runs where

Everything is in one namespace (`urumi`), installed by one Helm release (`urumi`) of the umbrella chart
`urumi-platform`, which depends on the reusable `woocommerce-store` chart (alias `woocommerce`).

```
namespace urumi
├── Deployments   urumi-gateway (1 local / 2 prod) · urumi-dashboard · urumi-store-wordpress
│                 urumi-store-mcp · urumi-fx-rates · urumi-team-notes
├── StatefulSets  urumi-postgres (PVC 1Gi) · urumi-store-mariadb (PVC 2Gi)
├── PVC           urumi-store-wordpress (2Gi, /var/www/html: themes, plugins, uploads)
├── Job (hook)    urumi-store-setup (post-install / post-upgrade, idempotent)
├── Services      all ClusterIP (no NodePort / LoadBalancer)
├── Ingress       urumi-store (store.localhost → wordpress:80)
│                 urumi-app   (app.localhost: /api,/mcp → gateway:8000, / → dashboard:8080)
├── Secrets       urumi-platform-secrets (secret-key, encryption-key, admin-password, postgres-password, fx-api-key)
│                 urumi-store-secrets    (mariadb passwords, wp-admin-password, wc key/secret, mcp-token)
│                 urumi-llm              (api-key, created by you, optional)
├── ConfigMap     urumi-gateway-config (seed list of upstream servers, no secrets)
└── NetworkPolicy default-deny + 6 allow rules (see SECURITY.md)
```

`make status` shows all of it.

## Probes, requests and limits

| Workload | Readiness | Liveness | Requests → Limits |
|---|---|---|---|
| gateway | `GET /readyz` (checks DB) | `GET /healthz` (+ startupProbe for first boot) | 100m/192Mi → 1/512Mi |
| dashboard | `GET /healthz` | `GET /healthz` | 10m/32Mi → 200m/128Mi |
| woocommerce MCP, fx-rates, team-notes | `GET /readyz` | `GET /healthz` | 50m/96Mi → 500m/256Mi (MCP), 20m/64Mi → 300m/192Mi |
| wordpress | `GET /wp-login.php` (PHP + DB) | `GET /wp-includes/images/blank.gif` (Apache) | 100m/256Mi → 1/768Mi |
| mariadb | `mariadb-admin ping -h 127.0.0.1` (TCP accepting) | TCP 3306 | 100m/256Mi → 1/768Mi |
| postgres | `pg_isready` | `pg_isready` | 50m/128Mi → 500m/512Mi |
| setup Job | n/a | n/a | 100m/192Mi → 1/512Mi |

Readiness = "send me traffic" (a pod that isn't ready is removed from the Service). Liveness = "restart me if
I'm stuck". Liveness checks are cheap and don't depend on other services, so a database outage doesn't
cause restart loops.

## Persistence

* MariaDB and Postgres use `volumeClaimTemplates`. WordPress uses a PVC. All use the default StorageClass
  (`local-path` on k3s/k3d), configurable via `persistence.storageClass` / `postgres.storageClass`.
* WordPress uses `strategy: Recreate` because its volume is ReadWriteOnce.
* Secrets and the WordPress PVC carry `helm.sh/resource-policy: keep`, so `helm uninstall` never deletes your
  data or passwords by accident.

## Public vs internal, and how it is enforced

| Layer | Mechanism |
|---|---|
| Only 2 hostnames are public | Ingress objects; every Service is `ClusterIP` |
| WooCommerce MCP not reachable from outside | no Ingress route + NetworkPolicy allows only `urumi.dev/mcp-client=true` pods + bearer token |
| Databases | NetworkPolicy: Postgres ← gateway; MariaDB ← WordPress + setup Job |
| Everything else | namespace-wide default-deny ingress policy |

## Local vs production: only values change

| Concern | `values-local.yaml` | `values-prod.yaml` |
|---|---|---|
| Domains | `store.localhost`, `app.localhost` | your domains |
| Scheme / TLS | http, no TLS | https, `cert-manager.io/cluster-issuer` annotation, TLS secrets |
| Images | `urumi/*:dev` built locally + `k3d image import` | `ghcr.io/<you>/urumi-*:<version>` built by CI |
| Secrets | generated by Helm (`lookup` keeps them stable) | `existingSecret` created out of band |
| Replicas | 1 | gateway 2, dashboard 2 |
| Storage | default sizes | `local-path`, larger sizes |
| Demo tools | `fx-rates__slow_operation` enabled for timeout demos | disabled |
| Cookies | not `Secure` | `Secure` (derived from scheme) |

## Upgrades and rollback

```bash
# upgrade one component: build/push a new tag, then
helm upgrade urumi deploy/helm/urumi-platform -n urumi -f values-prod.yaml \
  --set gateway.image.tag=1.1.0 --wait --timeout 10m
helm history urumi -n urumi          # every upgrade is a numbered revision
helm rollback urumi <REVISION> -n urumi --wait
```

* **Gateway / MCP servers / dashboard:** stateless Deployments → rolling update. A new pod must pass readiness
  before an old one is removed, so a bad image never takes traffic. `helm rollback` restores the previous
  image and config.
* **Gateway schema:** tables are created at startup (`create_all`, additive). For destructive migrations,
  add Alembic and run it as a pre-upgrade hook Job.
* **Store:** WordPress core/plugins live on the PVC, so update them with WP-CLI
  (`kubectl exec deploy/urumi-store-wordpress -- wp plugin update woocommerce --allow-root`) or wp-admin.
  The setup Job runs again after every `helm upgrade` and is idempotent.
  **Back up first:**
  `kubectl exec sts/urumi-store-mariadb -- mariadb-dump -uroot -p"$PW" wordpress > backup.sql`.
  Rolling back a DB schema change means restoring that dump, which `helm rollback` doesn't do.
* **Secrets:** never rotated by upgrades (`lookup`). To rotate the encryption key, put the new key first:
  `encryption-key: "new,old"`. Old ciphertexts still decrypt, new ones use the new key.
